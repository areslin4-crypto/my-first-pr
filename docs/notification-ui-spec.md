## 1. 背景與目標

### 1.1 背景

目前與 Claude（Claude Code 雲端工作階段）互動時，必須打開瀏覽器或桌面 App 才能：

1. 交付新的任務（例如「幫我修這個 bug」、「寫一份報告」）。
2. 知道任務是否已經完成。

當任務執行時間較長（數分鐘到數小時），使用者不會一直盯著畫面，導致「任務早就做完了，但我不知道」的狀況。

### 1.2 目標

建立一個手機上隨手可用的通知與溝通介面，讓使用者可以：

- **雙向溝通**：在 LINE 或 iMessage 直接用自然語言告訴 Claude 要做什麼。
- **完成通知**：Claude 完成（或卡住、需要決定）時，主動推播到手機。
- **快速回應**：在通知卡片上一鍵回覆「確認 / 看結果 / 繼續做 / 取消」。

### 1.3 成功指標（KPI）

| 指標 | 目標值 |
|---|---|
| 任務完成到使用者收到通知的延遲 | ≤ 10 秒（P95） |
| 通知送達率 | ≥ 99% |
| 使用者從手機下達任務後，工作階段開始執行的時間 | ≤ 30 秒 |
| 每日主動推播次數（避免騷擾） | 每個任務最多 3 則（開始 / 需要決定 / 完成） |

## 2. 使用者與情境

### 2.1 目標使用者

- 單一主要使用者（個人開發者 / 專案負責人），使用 iPhone 與 LINE。
- 第二階段可擴充到小型團隊（LINE 群組 / 多人 iMessage）。

### 2.2 核心情境

| 編號 | 情境 | 通道 |
|---|---|---|
| S1 | 使用者在外面，用 LINE 傳「幫我把 README 加上安裝步驟」，Claude 開始執行。 | LINE |
| S2 | Claude 完成任務後，推播「✅ 已完成：README 已更新，已推送到分支 xxx」，附上 PR 連結。 | LINE / iMessage |
| S3 | Claude 遇到需要使用者決定的事（例如兩種做法要選一個），推播問題並提供選項按鈕。 | LINE（Quick Reply）/ iMessage（文字回覆） |
| S4 | CI 失敗或任務卡住，推播「⚠️ 需要你看一下」並附錯誤摘要。 | LINE / iMessage |
| S5 | 使用者回覆「好，照方案 A 做」，Claude 繼續執行。 | LINE / iMessage |
| S6 | 使用者傳「目前有哪些任務在跑？」，Claude 回覆任務清單與狀態。 | LINE / iMessage |

## 3. 通道比較與選擇

### 3.1 LINE

| 面向 | 說明 |
|---|---|
| 官方 API | **LINE Messaging API**（需建立 LINE 官方帳號）。可接收 Webhook、主動推播（Push Message）、Flex Message 卡片、Quick Reply 按鈕。 |
| 舊方案 | LINE Notify 已於 2025 年 3 月底終止服務，**不可再採用**，一律改用 Messaging API。 |
| 費用 | 免費方案有每月免費推播則數上限（以 LINE 官方帳號當期方案為準，撰寫時台灣輕用量方案約 200 則/月），超過需升級。回覆訊息（Reply Message，在使用者傳訊後約 1 分鐘內回覆）不計入推播額度。 |
| 優點 | 官方 API 完整、介面豐富（卡片、按鈕）、跨平台（iPhone / Android / 電腦）。 |
| 缺點 | 需申請官方帳號；推播有額度；訊息需經 LINE 伺服器。 |

### 3.2 iPhone iMessage

iMessage **沒有**對一般開發者開放「由伺服器主動發送訊息給任意使用者」的官方 API。可行方案如下：

| 方案 | 做法 | 適合對象 | 限制 |
|---|---|---|---|
| A. Apple Messages for Business | 註冊企業帳號，透過 Apple 認可的訊息服務供應商（MSP）串接。 | 公司、正式產品 | 申請流程長、需企業身分、個人幾乎無法使用。 |
| B. 自架 Mac 中繼（推薦個人使用） | 一台常開的 Mac 登入同一 Apple ID 的「訊息」App，透過 AppleScript / Shortcuts 或開源中繼程式（如 BlueBubbles）把訊息送進 iMessage，並監聽收到的訊息。 | 個人開發者 | 需要一台 24 小時開機的 Mac；屬於非官方做法，macOS 更新可能造成失效。 |
| C. iOS 捷徑（Shortcuts）自動化 | iPhone 上建立捷徑，定時或由推播觸發後呼叫後端 API 取結果，再用「傳送訊息」動作送出 iMessage。 | 只想要單向通知 | 無法做到即時雙向，且 iPhone 需解鎖或有互動限制。 |
| D. 改用 APNs 推播（自製 iOS App） | 不走 iMessage，改做一個極簡 iOS App 接收 Apple Push Notification。 | 想要原生通知體驗 | 要寫 App、要 Apple 開發者帳號（年費）。 |

**結論**：

- **主通道：LINE Messaging API**。官方支援、雙向、卡片按鈕完整，是 MVP 的核心。
- **副通道：iMessage（方案 B 自架 Mac 中繼）**。做為「完成通知」的第二路徑，確保 iPhone 鎖定畫面一定會跳出。若無常開 Mac，退回方案 C 單向通知。
- 兩個通道共用同一個「通知中繼伺服器」，訊息內容只寫一次，由中繼層決定送到哪裡。

## 4. 系統架構

```
┌─────────────┐   Webhook    ┌──────────────────────┐   send_message /   ┌──────────────────┐
│  LINE App   │ ───────────▶ │                      │   create_session   │  Claude Code     │
│  (iPhone)   │ ◀─────────── │   通知中繼伺服器      │ ─────────────────▶ │  雲端工作階段     │
└─────────────┘  Push/Reply  │   (Notification Hub) │ ◀───────────────── │  (執行任務)       │
                             │                      │   任務事件 Webhook  └──────────────────┘
┌─────────────┐  iMessage    │  - 身分驗證           │
│  iMessage   │ ◀──────────▶ │  - 任務狀態資料庫     │
│  (iPhone)   │  Mac 中繼    │  - 訊息模板/路由      │
└─────────────┘              └──────────────────────┘
```

### 4.1 元件說明

| 元件 | 職責 |
|---|---|
| LINE 官方帳號 | 接收使用者訊息（Webhook）、發送推播與回覆。 |
| iMessage 中繼（Mac） | 將中繼伺服器的訊息送進 iMessage；把使用者在 iMessage 的回覆轉送回中繼伺服器。 |
| 通知中繼伺服器 | 核心。驗證來源、把訊息對應到 Claude 工作階段、記錄任務狀態、套用訊息模板、決定送 LINE 還是 iMessage 或兩者。 |
| Claude Code 雲端工作階段 | 實際執行任務。任務開始 / 需要決定 / 完成 / 失敗時，呼叫中繼伺服器的事件 API。 |

### 4.2 任務生命週期與對應通知

| 狀態 | 觸發 | 通知內容 | 是否推播 |
|---|---|---|---|
| `received` | 使用者傳訊 | 「收到，開始處理：<任務摘要>」 | 用 Reply（不耗推播額度） |
| `running` | 工作階段開始執行 | 不通知（避免騷擾） | 否 |
| `needs_input` | Claude 需要使用者決定 | 問題 + 選項按鈕 | 是 |
| `completed` | 任務完成 | 成果摘要 + 連結（PR / 檔案 / 報告） | 是 |
| `failed` | 錯誤或 CI 失敗 | 錯誤摘要 + 「重試 / 看詳細 / 取消」 | 是 |
| `cancelled` | 使用者取消 | 「已取消」 | 用 Reply |

## 5. 通知介面設計（UI）

### 5.1 設計原則

1. **一眼看懂**：第一行就是狀態 Emoji + 任務名稱。
2. **不超過一個螢幕**：摘要 3 行以內，細節放連結。
3. **可以直接行動**：每則通知最多 3 個按鈕，不需要打字。
4. **同一任務同一串**：用任務編號（例如 `#T-042`）貫穿所有訊息，方便對照。
5. **安靜時段**：預設 23:00 ~ 08:00 不推播，改為隔天早上彙整一則（可在設定中關閉）。

### 5.2 LINE 訊息模板

#### (a) 收到任務（Reply Message）

```
📥 已收到任務 #T-042
「把 README 加上安裝步驟」

預估：約 5 分鐘
我完成後會通知你。
```

#### (b) 任務完成（Flex Message 卡片）

```
┌──────────────────────────────┐
│ ✅ 任務完成  #T-042           │
│ 把 README 加上安裝步驟        │
├──────────────────────────────┤
│ • 新增「安裝」章節（12 行）    │
│ • 測試全部通過（3/3）         │
│ • 已推送分支 claude/readme-… │
├──────────────────────────────┤
│ [ 查看 PR ] [ 繼續修改 ] [ 👍 ] │
└──────────────────────────────┘
```

- 「查看 PR」：URI 按鈕，開啟 GitHub。
- 「繼續修改」：Postback，進入追問模式（下一則使用者文字會接到同一任務）。
- 「👍」：Postback，標記任務結案。

#### (c) 需要你決定（Quick Reply）

```
❓ 需要你決定  #T-042

安裝步驟要放哪裡？
A. 放在 README 最上方
B. 另外開一個 INSTALL.md

[ A ] [ B ] [ 都不要，先停 ]
```

#### (d) 失敗 / 卡住

```
⚠️ 任務卡住  #T-042

CI 失敗：test_hello.py 第 12 行
AssertionError: 'Hello, GitHub!' != 'Hello, World!'

[ 幫我修 ] [ 看完整日誌 ] [ 取消任務 ]
```

#### (e) 查詢狀態（使用者輸入「狀態」或「list」）

```
📋 目前任務

🟢 #T-042 README 安裝步驟 — 執行中 (3 分)
🟡 #T-041 補單元測試 — 等你決定
✅ #T-040 修 typo — 已完成 10:32
```

### 5.3 iMessage 訊息模板

iMessage 沒有卡片與按鈕，改用純文字 + 編號選項，使用者回覆數字或關鍵字即可。

```
✅ [Claude] 任務完成 #T-042
把 README 加上安裝步驟

• 新增「安裝」章節
• 測試 3/3 通過
• PR：https://github.com/…/pull/2

回覆 1 = 繼續修改，2 = 結案
```

```
❓ [Claude] 需要你決定 #T-042
安裝步驟要放哪裡？
1 = README 最上方
2 = 另開 INSTALL.md
0 = 先停
```

### 5.4 指令設計（兩通道共用）

| 使用者輸入 | 行為 |
|---|---|
| 任意自然語言 | 建立新任務（若目前沒有「追問中」的任務）。 |
| `狀態` / `list` | 列出進行中與最近完成的任務。 |
| `#T-042 <文字>` | 針對指定任務追問或補充。 |
| `取消 #T-042` | 取消任務。 |
| `安靜` / `勿擾` | 開啟勿擾 8 小時。 |
| `幫助` / `help` | 顯示指令列表。 |

## 6. 安全與隱私

| 風險 | 對策 |
|---|---|
| 陌生人加 LINE 官方帳號後下指令 | 白名單：只接受已綁定的 LINE userId；首次綁定需輸入一次性驗證碼。 |
| Webhook 偽造 | 驗證 LINE 的 `X-Line-Signature`；iMessage 中繼與中繼伺服器之間使用共享密鑰 + HTTPS。 |
| 通知洩漏敏感內容 | 通知只送「摘要 + 連結」，不送程式碼全文、金鑰、環境變數。 |
| 任務被濫發 | 每個使用者同時最多 5 個進行中任務；每分鐘最多 10 則訊息。 |
| 高風險動作（刪除、強制推送、對外發送） | 一律先推播「需要你決定」卡片，取得明確確認才執行。 |

## 7. 技術實作建議

### 7.1 中繼伺服器

- 語言 / 框架：Python（FastAPI）或 Node.js（Express），擇一即可，以團隊熟悉為主。
- 資料庫：SQLite（個人）或 PostgreSQL（團隊），儲存 `tasks`、`users`、`channels`、`messages`。
- 部署：任一支援 HTTPS 的雲端服務（LINE Webhook 必須是 HTTPS）。

### 7.2 與 Claude Code 的串接

1. **使用者 → Claude**：中繼伺服器收到訊息後，建立或喚醒一個 Claude Code 雲端工作階段，並把訊息作為提示送入。
2. **Claude → 使用者**：工作階段在關鍵節點（開始、需要決定、完成、失敗）呼叫中繼伺服器的 `POST /events` API，並附上任務編號、狀態、摘要、連結。
3. **追問**：中繼伺服器記錄「任務編號 ↔ 工作階段 ID」對應，後續訊息直接送回同一工作階段，保留上下文。

### 7.3 事件 API 草案

```http
POST /events
Content-Type: application/json
Authorization: Bearer <relay-token>

{
  "task_id": "T-042",
  "status": "completed",            // received | needs_input | completed | failed | cancelled
  "title": "把 README 加上安裝步驟",
  "summary": ["新增「安裝」章節（12 行）", "測試全部通過（3/3）"],
  "links": [{ "label": "查看 PR", "url": "https://github.com/..." }],
  "options": [],                    // needs_input 時提供選項
  "channels": ["line", "imessage"]  // 省略則依使用者偏好
}
```

### 7.4 iMessage 中繼（方案 B）最小做法

- Mac 常駐一個小程式，監聽中繼伺服器（WebSocket 或輪詢）。
- 收到要送出的訊息時，透過 AppleScript 控制「訊息」App 傳送給指定電話 / Apple ID。
- 讀取「訊息」的本機資料庫（`chat.db`）偵測新回覆，轉送回中繼伺服器。
- 需在 macOS 設定給予「自動化」與「完整磁碟取用」權限。

## 8. 開發階段規劃

| 階段 | 範圍 | 交付物 | 預估 |
|---|---|---|---|
| Phase 0 | 申請 LINE 官方帳號、建立 Messaging API Channel、設定 Webhook。 | 可收到測試訊息並回「收到」。 | 1 天 |
| Phase 1（MVP） | 中繼伺服器 + 任務狀態 + LINE 完成通知（純文字）。Claude 任務完成時推播。 | S1、S2 可用。 | 3 ~ 5 天 |
| Phase 2 | Flex Message 卡片、Quick Reply、需要決定 / 失敗通知、狀態查詢指令。 | S3 ~ S6 可用。 | 3 ~ 5 天 |
| Phase 3 | iMessage 副通道（Mac 中繼），通道偏好設定，勿擾時段。 | iPhone 鎖定畫面雙通道通知。 | 3 ~ 5 天 |
| Phase 4 | 多使用者 / LINE 群組、每日彙整、使用統計。 | 團隊版。 | 視需求 |

## 9. 驗收標準（MVP）

- [ ] 在 LINE 傳「幫我把 README 加上安裝步驟」，30 秒內收到「已收到 #T-xxx」回覆。
- [ ] 任務完成後 10 秒內，LINE 收到含 PR 連結的完成通知。
- [ ] 非白名單的 LINE 帳號傳訊，只會收到「尚未綁定」提示，不會建立任務。
- [ ] 偽造的 Webhook 請求（簽章錯誤）被拒絕並記錄。
- [ ] 通知內容不包含任何金鑰或完整程式碼。

## 10. 待討論事項

1. iMessage 是否有一台可常開的 Mac？沒有的話 Phase 3 改為「iOS 捷徑單向通知」或直接略過，只用 LINE。
2. LINE 推播免費額度是否足夠？若每日任務數 > 6，建議升級方案或把「開始」訊息全部改為 Reply。
3. 完成通知是否要附上成果的簡短預覽（例如 diff 前 5 行）？會增加洩漏風險，預設關閉。
4. 是否需要語音訊息輸入（LINE 語音 → 文字）？屬於 Phase 4 以後。
